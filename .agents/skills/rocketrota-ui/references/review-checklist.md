# UI review checklist

Check the states and interactions affected by the task. For design-only work, use the same checks to specify what the design should show and report it as a design evaluation.

- **First useful information.** At phone width, identify the page scope and next action from the initial viewport. At desktop width, compare the key records without hunting for detached filters or legends. Check heading scale, aligned edges, scan rhythm, long names, numeric alignment and the contrast of small metadata.
- **Composition.** Check each border, card and section gap against the information it groups. Remove redundant wrappers or decoration where they cost screen space. Check that blue draws attention to action or selection and that semantic status remains understandable in text.
- **Responsive behavior.** Inspect the rendered screen at a narrow phone width (about 360–390 px) and a desktop width (about 1280–1440 px). Check the actual layout breakpoint and a short viewport when sticky elements or overlays are involved. Look for clipped fields, page-level overflow, obscured focus, competing scroll regions and unusable touch targets. Verify device safe areas and keyboard behavior when the environment supports them.
- **Interaction and accessibility.** Exercise the primary action with keyboard and touch or pointer as applicable. Check focus visibility, dialog focus return and dismissal, accessible names, reading order, non-colour status cues, contrast, and reduced motion. For a board change, try the non-drag path. Test any supported theme affected by the change.
- **States and data.** Check loading or refresh, empty and no-results states, a failure with recovery, and pending, disabled or success states where they apply. Use realistic fixtures such as a long employee name, an overnight shift or a missing clock-out. Verify role, location, date and timezone context after navigation and mutation.
- **Technical fit.** Reuse the shared shell, variants, query options, hooks and formatters that own the behavior. Check that route loading and lazy boundaries still hold, especially for boards and dialogs. Run the relevant targeted Vitest tests and applicable lint or type checks from `package.json`. Inspect the rendered result again after fixes and state any limitations in the handoff.
